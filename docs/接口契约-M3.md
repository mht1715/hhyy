# M3 接口契约（前端 ↔ 后端）

> 这份文档是 M3 前后端并行开发的**唯一契约**。改动顺序：先改这里 → 两边同时改。
> M2 的契约（`docs/接口契约-M2.md`）继续有效，本文只写**新增与变更**部分。

M3 有两块能力：

1. **记忆**：短期（会话窗口 + 滚动摘要）+ 长期（结构化画像 + 语义记忆），用户可查看/删除/关闭。
2. **转人工**：触发 → 建单排队 → 坐席接管 → 双向消息 → 结束/离线留言。

贯穿两条铁律：

- **记忆永不跨用户**：所有读写都以 `user_id` 为第一维度，接口层再从 token 取 `user_id`，不接受前端传。
- **AI 静默可判定**：会话进入 `human_active` 后，`/api/chat/stream` 不再调模型，只落库 + 返回 `silenced=true`。

---

## 1. 会话状态

`conversations.status` 的取值与流转（PRD FR5.2）：

```
bot_active ──触发转人工──▶ handoff_pending ──坐席接管──▶ human_active ──结束──▶ closed
                                   │
                                   └──90s 无坐席/用户留言──▶ ticket_offline（会话仍 closed）
```

前端只需要认这 4 个值：`bot_active` / `handoff_pending` / `human_active` / `closed`。
`ticket.status` 另有 `queued` / `assigned` / `resolved` / `offline` 四个值。

## 2. `POST /api/chat/stream`（M3 变更）

请求体与 M2 完全一致，**不需要**新增字段。变化在响应帧上。

### 2.1 `meta` 增加状态

```json
{
  "conversation_id": "c_1",
  "message_id": "m_1",
  "trace_id": "tr_1",
  "replayed": false,
  "status": "bot_active",
  "memory": {"enabled": true, "count": 3},
  "ticket": null
}
```

- `status`：见 §1。前端进页面/刷新时靠它还原 `HandoffBar`。
- `memory.enabled`：`false` 时前端不展示「已参考记忆」徽标（用户关过记忆）。
- `ticket`：当前会话的活跃工单，无则 `null`；有则同 §5.1 的 `ticket` 结构（含 `queue_position`、`queue_expires_in`）。

### 2.2 新增 `memory` 事件（在 `route` 之后、`delta` 之前）

```json
{
  "items": [
    {"id": "9f2…", "type": "fact", "content": "对青霉素过敏", "score": 0.91,
     "source_message_id": "m_8", "created_at": "2026-11-10T09:12:00"}
  ],
  "profile": {"summary": "慢病患者，偏好颗粒剂", "enabled": true},
  "injected": true
}
```

- `type` ∈ `fact` / `preference` / `episode` / `risk`。
- `injected=false` 表示取到了记忆但本轮和问题不相关、没有塞进 prompt（前端只显示不提示）。
- 回答里若用到记忆，后端会以「您上次提到…」的措辞体现，并带 `source_message_id` 供溯源。

### 2.3 `handoff` 事件改为真实工单

```json
{"ticket_id": "t_1", "queue_position": 1, "queue_expires_in": 88,
 "reason": "用户点击转人工", "trigger": "explicit", "status": "queued"}
```

- `trigger` ∈ `explicit`（用户点按钮）/ `agent_tool`（模型调 `escalate_human`）/ `sensitive`（投诉、医疗纠纷、过量、自杀倾向…）/ `refusal`（连续 2 次拒答，只建议不强转）/ `emotion`（连续 2 轮负面情绪，只建议）。
- `refusal` / `emotion` 只发 `suggested_actions`（`{"type":"handoff","label":"转人工客服"}`），**不建工单**。
- 真实建单的 `handoff` 事件一定带 `ticket_id`。

### 2.4 `done` 增加字段

```json
{"status": "handoff_pending", "ticket": {"ticket_id": "t_1", "queue_position": 1},
 "silenced": false, "memory_used": 1}
```

### 2.5 `human_active` 时的特殊流

```
meta(status=human_active, ticket={...}) → done(silenced=true, status=human_active)
```

没有 `route` / `agent` / `delta` / `citation`：AI 不出声，用户消息已落库并推给坐席。
前端收到 `silenced=true` 时不要显示「AI 正在输入」，改为「客服已接入，消息将由客服回复」。

## 3. 记忆接口

### 3.1 `GET /api/me/memory`

权限：登录（`patient` / `doctor` / `support` / `admin`）。游客 401。

```json
{
  "code": 200, "message": "ok",
  "data": {
    "enabled": true,
    "profile": {"summary": "慢病患者，偏好颗粒剂", "attributes": {"prefer": "颗粒剂"}, "updated_at": "2026-11-18T10:00:00"},
    "items": [
      {"id": "9f2…", "type": "fact", "content": "对青霉素过敏", "confidence": 0.95,
       "sensitive": false, "source_message_id": "m_8",
       "source_conversation_id": "c_1", "created_at": "2026-11-10T09:12:00",
       "expires_at": "2027-05-09T09:12:00"}
    ],
    "stats": {"total": 12, "by_type": {"fact": 5, "preference": 3, "episode": 3, "risk": 1}}
  }
}
```

按 `created_at` 倒序，默认 50 条。`source_message_id` 用于「这条是从哪句话记下来的」溯源（前端可只展示时间）。

### 3.2 `DELETE /api/me/memory/{id}`

```json
{"code": 200, "message": "ok", "data": {"deleted": true}}
```

只删自己的；别人的 id 一律 `deleted:false`（不区分「不存在」与「不是你的」，避免探测）。

### 3.3 `DELETE /api/me/memory`

```json
{"code": 200, "message": "ok", "data": {"deleted": 12}}
```

一键清空（含语义记忆向量）。

### 3.4 `PATCH /api/me/memory`

```json
{"enabled": false}
```

```json
{"code": 200, "message": "ok", "data": {"enabled": false}}
```

关闭后：**不再写入新记忆**，也不再往 prompt 注入；历史条目保留，可继续删除。重新打开即恢复。

## 4. 会话接口

### 4.1 `GET /api/conversations`

权限：登录。只返回自己的会话（`support`/`admin` 带 `?scope=all` 时返回全部，用于工作台）。

```json
{"code": 200, "message": "ok",
 "data": [{"id": "c_1", "title": "花红片怎么吃", "agent_code": "drug_consult",
           "status": "handoff_pending", "channel": "web",
           "ticket": {"ticket_id": "t_1", "status": "queued", "queue_position": 1},
           "updated_at": "2026-11-18T10:00:00"}]}
```

### 4.2 `GET /api/conversations/{id}`

权限：会话本人，或 `support`/`admin`。

```json
{"code": 200, "message": "ok",
 "data": {
   "id": "c_1", "title": "…", "agent_code": "drug_consult", "status": "human_active",
   "ticket": {"ticket_id": "t_1", "status": "assigned", "queue_position": 0,
              "reason": "用户点击转人工", "trigger": "explicit",
              "risk_flags": ["投诉"], "summary": {"intent": "…", "entities": [], "tried_steps": [],
              "unresolved": "…", "risk_flags": [], "suggested_reply": "…"},
              "assigned_to": "客服小王"},
   "messages": [
     {"id": "m_1", "role": "user", "content": "我要投诉", "created_at": "…"},
     {"id": "m_2", "role": "assistant", "content": "…", "citations": [], "contributors": []},
     {"id": "m_3", "role": "human_agent", "content": "您好，我是客服小王", "actor_name": "客服小王"}
   ]
 }
}
```

`role` ∈ `user` / `assistant` / `human_agent`（新增，前端要单独渲染气泡样式）/ `system`。

## 5. 转人工接口

### 5.1 `POST /api/handoff`

权限：登录（游客 401，前端提示登录）。`conversation_id` 必填且必须属于自己。

```json
{"conversation_id": "c_1", "reason": "投诉药品不良反应"}
```

```json
{"code": 200, "message": "ok",
 "data": {"ticket_id": "t_1", "status": "queued", "queue_position": 1,
          "queue_expires_in": 90, "reason": "投诉药品不良反应", "trigger": "explicit",
          "conversation_id": "c_1"}}
```

幂等：同一会话已有活跃工单（`queued`/`assigned`）时直接返回该工单，`queue_position` 重算，不重复建单。

### 5.2 `POST /api/handoff/offline`

90s 无人接管后由前端提交留言（PRD FR5.3/FR5.8）。

```json
{"conversation_id": "c_1", "name": "张三", "contact": "13800000000", "demand": "希望回电说明"}
```

```json
{"code": 200, "message": "ok",
 "data": {"ticket_id": "t_1", "status": "offline", "saved": true}}
```

- 把 `{name, contact, demand}` 写进 `handoff_tickets.summary.offline` 并置 `status=offline`；
- `queue_expires_in` 已为 0 时前端才展示表单；后端不强制（允许用户提前留言）。

### 5.3 坐席接口（`support` / `admin`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/support/tickets?status=queued` | 队列列表（默认 `queued,assigned`） |
| POST | `/api/support/tickets/{id}/accept` | 接管：`queued → assigned`，会话 `→ human_active` |
| POST | `/api/support/tickets/{id}/resolve` | 结束：`assigned → resolved`，会话 `→ closed` |
| POST | `/api/support/tickets/{id}/messages` | 坐席发消息（落库 + 广播） |

`GET /api/support/tickets` 返回：

```json
{"code": 200, "message": "ok",
 "data": [{"ticket_id": "t_1", "status": "queued", "queue_position": 1,
           "wait_seconds": 42, "user_label": "patient_1 / 138****0000",
           "risk_flags": ["投诉"], "trigger": "sensitive",
           "summary": {"intent": "…", "suggested_reply": "…"},
           "conversation_id": "c_1", "conversation_title": "花红片怎么吃",
           "created_at": "2026-11-18T10:00:00"}]}
```

`POST .../accept` → `{"ticket_id": "t_1", "status": "assigned", "conversation_id": "c_1", "status_of_conversation": "human_active"}`

`POST .../messages` body `{"content": "您好，我是客服小王"}` → `{"message_id": "m_3", "delivered": true}`

非法状态流转（例如接管一个 `resolved` 工单）返回 **409** + `{"detail": "工单状态不允许该操作：resolved → assigned"}`。

### 5.4 `POST /api/support/ws-ticket`

权限：登录。用「先 HTTP 拿短期 ticket 再连 WS」的方式鉴权，**避免 JWT 进 query string 被日志记录**。

`conversation_id` 是**可选** query 参数（`?conversation_id=...`）：

- 带上：顺手校验归属/角色，并把会话绑进票据（换错会话连不上）；
- 不带：票据只证明身份，权限在 WS 握手时按 URL 里的会话再校验一次。

```json
{"code": 200, "message": "ok",
 "data": {"ws_ticket": "wst_9f2…", "expires_in": 60,
          "ws_url": "/ws/support/c_1"}}
```

`ws_url` 在未传 `conversation_id` 时为空串（前端自己拼）。票据一次性，重连要重新换一张。

## 6. `WS /ws/support/{conversation_id}`

鉴权：连接建立后**第一帧**必须是 `auth`（不放在 URL 里）。

客户端 → 服务端：

```json
{"type": "auth", "ticket": "wst_9f2…"}
{"type": "message", "content": "您好，我是客服小王"}
{"type": "pong"}
```

服务端 → 客户端：

```json
{"type": "ready", "role": "support", "conversation_id": "c_1", "status": "human_active", "name": "客服小王"}
{"type": "message", "message": {"id": "m_3", "role": "human_agent", "content": "…", "actor_name": "客服小王", "created_at": "…"}}
{"type": "message", "message": {"id": "m_4", "role": "user", "content": "…", "created_at": "…"}}
{"type": "status", "status": "human_active", "ticket": {"ticket_id": "t_1", "queue_position": 0}, "by": "客服小王"}
{"type": "error", "code": "FORBIDDEN", "message": "无权进入该会话"}
```

- 允许进入的角色：会话本人（`role: user`）或 `support`/`admin`（`role: support`）。
- 坐席只有在**接管后**才能发消息；未接管时发消息返回 `{"type":"error","code":"NOT_ASSIGNED"}`。
- 90s 超时由前端计时（用 §5.1 返回的 `queue_expires_in`），后端只落库。
- 服务端每 25s 发 `{"type":"ping"}`；客户端 90s 无任何帧就重连（指数退避，上限 10s）。
- 会话结束（`closed`）服务端广播 `status` 后**不主动断开**，由客户端关闭；重新开会话要新建。

> 多进程一致性靠 Redis Pub/Sub（channel `hhyy:support:{conversation_id}`）；Redis 不可用时退化为**进程内广播**（单进程演示仍然可用），并在 `/health` 里能看到 `redis` 状态。

## 7. 前端要做的四件事

1. `components/agent/HandoffBar.vue`：5 个状态（`idle` / `queued` / `human_active` / `offline` / `closed`），排队倒计时用 `queue_expires_in` 递减，归零切留言表单。
2. `views/MemoryView.vue`（`/me/memory`）：列表 + 删除 + 一键关闭；关闭后顶部提示「已关闭记忆，AI 不再记录」。
3. `views/SupportView.vue`（`/support`，`support`/`admin` 可见）：待接入队列（等待时长、风险标记、交接摘要）+ 会话详情 + 接管/发消息/结束。
4. `composables/useSupportSocket.js`：拿 `ws_ticket` → 连 WS → 第一帧 `auth` → 断线重连（退避）+ 心跳 `pong`；把 `message`/`status` 帧回调给页面。

`human_agent` 消息气泡要与 AI 气泡区分（左侧、蓝色、头像「客服」），并在会话头部提示「人工客服已接入」。

## 8. 实现备注（联调时确认过的细节）

1. **时间一律 UTC + `Z`**：所有 `created_at` / `updated_at` / `expires_at` 都是 `2026-11-18T15:45:19.158741Z`。
   库里的列是 naive UTC（PG 容器时区 `Etc/UTC`），出口统一补 `Z`——否则浏览器按本地时间解析，
   「等了 3 分钟」会显示成 8 小时。等待时长优先用服务端给的 `wait_seconds`，不要自己减时间。
2. **会话校验前置**：`conversation_id` 不存在/无权时，`/api/chat/stream` 直接返回 **404/403**（普通 JSON），
   不会先回 200 再在流里报错。
3. **记忆相关度门槛 0.30**（余弦）：低于门槛的记忆不注入。实测相关用药问题 0.36~0.58、
   无关问题（退款）0.17~0.25。小样本，换 embedding 模型要重新标定。
4. **`silenced` 流的 `meta.message_id` 为空**：这一轮没有 AI 回答，不产生 assistant 消息；
   用户消息的 id 在 `done.message_id` 里。
5. **WS 会回显自己发的消息**：因为广播是「一个会话一条频道」，发送方也会收到自己的帧。
   `message` 帧带 `client_message_id`（客户端发的原样回带），前端发消息时先插一条本地气泡、
   收到回显后按 `client_message_id` 认领（换成服务端 `id`），这样既有即时感又不会显示两遍。
6. **工单状态流转错误返回 409**，`detail` 是可直接展示的中文（如「工单状态不允许该操作：assigned → assigned」）。
7. **AI 静默只针对 `human_active`**：`handoff_pending`（还在排队）时 AI 照常回答，
   只是每轮 `done.status=handoff_pending`、`meta.ticket` 带上排队信息。
8. **实时通道在排队阶段就要连上**（`status=handoff_pending` 即连），只在 `human_active` 才连会死锁：
   前端永远等不到「客服已接入」那一帧。`ready`/`status` 帧的 `status` 就是会话状态，直接覆盖本地状态。
9. **`status` 帧带完整工单**（`ticket_payload`：`ticket_id/status/queue_position/queue_expires_in/assigned_to/…`），
   前端不必为了一次状态变化再查接口。
10. **对话恢复靠 URL**：Agent 页用 `?c=<conversation_id>`，客服工作台用 `?ticket=<ticket_id>`。
    刷新后按参数拉 `GET /api/conversations/{id}` 还原消息、`status`、`ticket`；
    新建会话时把 `c` 换掉，点「新会话」时删掉。
11. **详情里的空 assistant 占位行不返回**：流式回答先落一条空行、正文在流结束才写回；
    `GET /api/conversations/{id}` 会过滤掉 `content` 为空的 assistant 行，避免坐席看到永远补不上的空气泡。
12. **坐席端对选中的会话做 3s 软刷新**：敏感场景在生成**之前**就建单，坐席点进来时 AI 那条消息可能还没写完；
   轮询负责兜底，WS 负责即时，两者同时存在不是冗余。
13. **「结束会话」= AI 接管，不是关会话**：`POST /tickets/{id}/resolve` 后工单 `resolved`、会话回到
   `bot_active`，`status` 帧也广播 `bot_active`；用户继续提问 AI 正常回答，再次转人工会建**新**工单。
   只有 90s 无人接管的留言（`offline`）才把会话置为 `closed`。
14. **`route` 事件可能多一个 `rewritten` 字段**：短句 + 指代词（这个药/它/刚才…）且有上文时，
   服务端会先做指代消解，`rewritten` 是**检索实际用的查询**；`meta` 里的用户原话不受影响。
15. **登录态按标签页隔离**：前端 `sessionStorage` 优先、`localStorage` 兜底。
   同一浏览器两个标签页可分别是患者 / 客服——否则后登录的会把前一个顶掉（表现为「消息都是同一方发的」）。
16. **`support` 也是「登录即可」的角色**：`app/api/deps.py` 的 `AnyUser` 已包含它；
   早期的 `[admin, doctor, patient]` 会让客服一登录就被购物车 403 顶掉，进不去 `/support`。
